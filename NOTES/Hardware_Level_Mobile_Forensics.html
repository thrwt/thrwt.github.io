Modern smartphones are, at the hardware level, small embedded computers built around a System-on-Chip (SoC), a package of non volatile flash storage, and a firmware chain that authenticates and loads each stage of software in sequence.

Mobile forensic examiners rarely need to think about this stack when a device is powered on, unlocked, and commercial tools such as Cellebrite UFED, Magnet AXIOM handle acquisition through supported logical interfaces. But a meaningful share of real casework involves devices that are locked, damaged, water exposed, or simply unsupported by any commercial extraction profile. In those cases, the examiner must fall back to hardware level acquisition, reading the flash memory directly, bypassing the operating system.

This research is organized in two halves that mirror how a forensic examiner should actually think about a device.

The first half covers the underlying hardware and software architecture, firmware and bootloaders, the two dominant families of embedded flash memory (eMMC and UFS), partition indexing via GPT, and storage particularities of the four SoC vendors most commonly encountered in the field MediaTek, Qualcomm, Exynos, and HiSilicon/Kirin.

Mobile Software & Firmware Architectures

At the lowest level of an Android device sits the firmware is fixed low level code responsible for bringing the SoC out of reset and initiating the boot chain, commonly referred to in the repair trade as the "first logo" stage. In forensic and firmware literature this stage is generally called the Bootloader, but its concrete name and structure differ by SoC vendor because each vendor implements its own proprietary boot ROM and secondary program loader :")

SoC VendorPrimary Program Loader Implementation
MediaTek (MTK)Preloader
Qualcomm (QLM)Aboot, XBL (eXtensible Boot Loader)
Spreadtrum / Unisoc (SPD)SPL (Secondary Program Loader)
Samsung ExynosSboot, CM (Core Module)
HiSilicon (Kirin)Xloader, Fastboot

The firmware operates as a gatekeeper. it initializes the primary memory controller, stages volatile DRAM, verifies cryptographic signatures on verified-boot platforms, and passes execution control downstream. If any of these software components fails an integrity or presence check, the boot process halts and the device typically becomes stuck at its manufacturer logo screen

Everything above the firmware layer the kernel, the recovery image, and the Android userspace is generally referred to as software.

Mobile Storage Technologies

Non volatile memory has evolved from ROM and PROM to EPROM, EEPROM, and then flash memory. NOR flash is mainly used for running code, while NAND flash is denser, cheaper, and better for storing large amounts of data. MMC added a controller to manage NAND flash, and eMMC integrated this technology into a package designed for mobile devices. Later, UFS replaced the older MMC interface with a faster serial connection, providing higher performance and more SSD-like storage capabilities for modern smartphones.

ROM → PROM → EPROM → EEPROM → NOR → NAND → MMC/SDCARD → eMMC/EMCP → UFS/EUFS

In research i will focus on MMC and UFS cuz is the most popular mobile storage in market

EMMC vs EMCP, UFS vs EUFS

  • eMMC →NAND storage with no integratedDRAM, packaged exclusively as BGA153.
  • EMCP (embedded Multi-Chip Package) → eMMC combined with integrated DRAM in the same package, found in BGA221 / BGA162 / BGA254 packages.
  • UFS →NAND storage with no integrated DRAM, packaged exclusively as BGA153.
  • EUFS → UFS combined with integrated DRAM, found in BGA254 / BGA297 packages.

eMMC Architecture

eMMC uses a parallel data bus, and its performance improved with newer versions. eMMC 4.5 supports up to 200 MB/s, while eMMC 5.0 and 5.1 can reach up to 400 MB/s. eMMC 5.1 also introduced Command Queuing (CQ), which improves performance when handling multiple read and write operations

eMMC packages contain an integrated controller that abstracts the underlying flash into distinct hardware level partitions

Hardware Block AliasStandard JEDEC PartitionTechnical Forensic Function
ROM1User Data AreaPrimary storage; contains the partition index (GPT) and all OS/user volumes.
ROM2Boot Partition 1 (BOOT1)Dedicated non-volatile boot mirror; holds primary bootloader images.
ROM3Boot Partition 2 (BOOT2)Secondary boot mirror for redundancy and fallback.

Vendor-Specific Boot Partition Routing

In standard embedded designs, the host SoC directs its primary boot fetch to the dedicated hardware boot partitions (BOOT1 or BOOT2)

  • IN MediaTek, Exynos, and Kirin : Platforms default to reading boot stages from the physical BOOT1 / BOOT2 partitions.
  • IN Qualcomm : Qualcomm application processors deviate from this convention by fetching primary boot routines directly from the User Data Area (ROM1). Misidentifyingthis behavior during physical ISP extraction will lead an examiner to mischaracterize a device's boot.

Pinouts

eMMC (legacy MMC-derived parallel bus):CMD (command line), CLK (clock), DAT0–DAT7 (up to 8 parallel data lines, depending on bus width configuration ), VCC (core supply), VCCQ (I/O supply).

UFS Architecture

UFS uses a newer full-duplex serial interface instead of the older parallel MMC bus.
It uses M-PHY and UniPro technologies with SCSI-based commands, providing much higher performance. UFS speeds increased from about 1.2–2.9 Gbps in UFS 1.x to 23.2 Gbps per lane in UFS 4.x. However, these are theoretical interface speeds.
The actual performance is lower because it depends on the NAND flash, controller, number of memory channels, temperature, and caching.

UFS VersionPhysical Link GearApprox. Speed per Lane
UFS 1.xHS-G1 / HS-G21.2–2.9 Gbps
UFS 2.0 / 2.1 / 2.2HS-G35.8 Gbps
UFS 3.0 / 3.1HS-G411.6 Gbps
UFS 4.0 / 4.1HS-G523.2 Gbps (~46.4 Gbps across dual lanes)

UFS replaces physical hardware partitions with SCSI Logical Units (LUNs). Dedicated boot LUNs typically designated Boot LUN A and Boot LUN B hold redundant stages of the initial bootloader.

SoC LUN Allocation

UFS organizes storage using Logical Units (LUNs) instead of the traditional physical partitions used by eMMC. Dedicated boot LUNs, usually Boot A and Boot B, store separate copies of the bootloader to provide redundancy. The exact LUN used for each boot stage depends on the SoC manufacturer and its Boot ROM configuration

SoC VendoreMMC Boot SourceUFS Boot Source
Samsung ExynosBOOT1 / BOOT2Boot A (LUN1) / Boot B (LUN2)
MediaTekBOOT1 / BOOT2Boot A (LUN0) / Boot B (LUN1)
HiSilicon (Kirin)BOOT1 / BOOT2Boot A (LUN0, Xloader) / Boot B (LUN1, Fastboot)
QualcommUser Area (ROM1)Boot A (LUN1: Primary GPT, XBL), Boot B (LUN2: Secondary GPT/Backup)

UFS communications operate across two M-PHY physical signaling profiles:

  • PWM-Gear (Pulse Width Modulation): Low-speed, low-power modes (PWM-G1 through PWM-G7) with throughputs ranging from 3 to 9 Mbps. PWM is used during link initialization, power-state negotiations, and recovery modes.
  • HS-Gear (High Speed): Multi-gigabit modes (HS-G1 through HS-G5) designed for system execution, app loading, and active read/write operations.

During forensic hardware diagnostics, forcing a UFS memory link back to its base PWM operating mode allows examiners to verify the electrical and signal integrity of the storage bus when higher-speed HS handshakes fail due to line noise or physical board damage

Pinouts

UFS (serial, differential, UniPro/M-PHY-based):
TX0P / TX0N (differential transmit pair, DIN0_T / DIN0_C),
RX0P / RX0N (differential receive pair, DOUT0_T / DOUT0_C),
CLK (reference clock), RESET, VCC (core supply), VCCQ1 and VCCQ2 (separate I/O supply rails, reflecting UFS's dual-voltage-domain design).

Storage Indexing & Android Volumes

Once a storage device initializes, the host processor interprets the data block layout via a partition table located at the head of the user data address space

Structural of Android Storage Volumes

  • Discrete Partition Architecture (Pre-Android 10): Independent EXT4 partitions allocated directly on flash (/system, /vendor, /boot, /recovery, /data, /efs).
    EFS holds cryptographic radio calibration data and the baseband IMEI.
  • Dynamic Partitions (superpartition, Android 10+): Consolidates runtime OS images (system, vendor, product, odm) into a single raw container partition designated super.
    This design improves storage allocation flexibility, but requires forensic carving tools to parse custom Device-Mapper-Linear metadata structures.

RPMB Binding Constraints

RPMB is a protected area in eMMC and UFS storage used to store important security information, such as anti-rollback counters and secure-boot data. It uses a secret authentication key and a write counter to make sure data is trusted and cannot be replayed or replaced with an older version. Unlike normal user storage, RPMB is designed to keep this security state even after a factory reset or re-flashing the device.

Mechanism

Authentication key
 A 256-bit symmetric key is programmed into the storage device once, at manufacturing time, in a controlled/secure environment.

Write authentication
Every RPMB write must include a Message Authentication Code (MAC), typically HMAC-SHA-256, computed over the write frame and the shared authentication key. Reads are unauthenticated by default but return data whose authenticity can be checked the same way.

Replay protection
 A monotonically increasing write counter, maintained by the storage device itself, is included in the MAC computation for every write.
Because the counter always increases, a captured (write request, MAC) pair cannot be successfully replayed later the counter value would no longer match, and the MAC would fail to verify.

JTAG acquisition is mainly used when a device cannot boot normally, USB debugging is unavailable, or the bootloader prevents other acquisition methods. It also requires the board to expose accessible JTAG/TAP test points. However, JTAG is usually not the first choice because it is more invasive, slower, and carries some risk of damaging the board. If logical, file-system, or standard physical acquisition works, those methods are generally preferred.

JTAG vs. ISP vs. Chip-Off

JTAG (Joint Test Action Group)

JTAG leverages the IEEE 1149.1 boundary scan interface originally designed for circuit integrity verification.
By soldering leads to the Test Access Port (TAP) comprising TDI (Data In), TDO (Data Out), TCK (Clock), and TMS (Mode Select) an examiner instructs the SoC's debug engine to halt execution and dump memory contents across the internal bus.

The TAP Controller is a 16-state system controlled by TCK (clock) and TMS (control). It decides whether the chip is reading, shifting, or updating data. The Instruction Register (IR) selects what operation the chip should perform, such as IDCODE, EXTEST, SAMPLE/PRELOAD, or BYPASS. After selecting an instruction, the corresponding Data Register (DR) is used to send or receive data through TDI/TDO. The Boundary-Scan Register (BSR) contains cells connected to the chip's I/O pins, allowing a tester to read or control the signals on the pins without directly accessing each pin individually.

Advantages, Limitations, Risks

JTAG forensic acquisition generally involves connecting directly to test points on the device's board using a JTAG adapter. The tool communicates with the SoC through its debug interface to access the device's memory without relying on the normal OS or bootloader. The acquired data is then saved as a raw image, immediately hashed (such as with SHA-256), and documented for chain of custody. Finally, the image is checked to make sure the expected partitions and filesystem structures are present before analysis.

limitations
JTAG has several limitations. It is not a universal way to bypass Android security and cannot automatically decrypt FBE/FDE-protected data. Some devices disable JTAG completely, while finding the correct test points can be difficult and may risk damaging the board. JTAG also only provides access to what the SoC and its current firmware state allow, so it does not guarantee a complete dump. Finally, JTAG procedures are often specific to the exact device and board revision, meaning a method that works on one version may not work on another.

ISP (In-System Programming)

ISP refers to directly interfacing with the storage chip's native protocol (the eMMC/MMC command bus, or the UFS UniPro/M-PHY link) while the chip remains soldered on the board.

ISP extraction reads the storage directly from the motherboard without using the phone's SoC. Very thin wires are soldered to test points connected to the memory's communication lines, such as DAT0, CMD, and CLK, along with power and ground. The memory chip stays on the board, while an external programming tool communicates with it and extracts the data.

eMMC ISP vs. UFS ISP

  • eMMC ISP connects to the CMD/CLK/DAT lines and issues standard eMMC bus commands directly, reading the User Data Area, Boot Partitions, and RPMB.
  • UFS ISP is more difficult than eMMC ISP because UFS uses a high-speed differential serial connection instead of simple parallel data lines. The examiner must correctly handle things like clocking, reset, and communication speed (gear) negotiation. If the external tool and UFS device do not use compatible settings, the storage may not be detected at all.

Advantages, Limitations, Risks

Advantages: does not require desoldering the chip, can work on devices where JTAG test points are unavailable or fused off, generally faster to set up than chip off once test points are identified.

ISP also has some limitations. It requires accurate identification of test points, which are often undocumented, and poor soldering or too much heat can damage the board or storage chip. UFS ISP is especially complex compared with eMMC ISP.
Also, the extracted raw image may still be encrypted, and ISP does not automatically provide access to RPMB, since RPMB requires its authentication key

Chip-Off

Chip-off acquisition physically desolders the NAND flash package (eMMC/UFS/EMCP/EUFS) from the PCB and reads it directly in a compatible chip reader/adapter, bypassing the SoC, bootloader, and OS entirely.

Chip-off acquisition involves removing the storage chip from the motherboard using controlled heating, then cleaning and sometimes re-balling the chip before placing it in a compatible reader or adapter. The reader then extracts the raw storage image. With eMMC, this can include the User Data Area and sometimes the Boot Partitions. For UFS, a UFS-capable reader is required because it uses the UniPro/M-PHY protocol, making UFS chip-off more specialized than eMMC.


Chip-off has several advantages. It can work even when the motherboard is severely damaged, as long as the storage chip is still intact. It also bypasses SoC-level restrictions, so things like a locked bootloader or disabled JTAG no longer matter. In addition, it can usually provide access to most or all readable NAND storage blocks, making it one of the most comprehensive physical acquisition methods.


Chip-off also has important disadvantages. It is destructive because the storage chip must be removed from the board, and the device may no longer be practical to restore. It requires specialized adapters that match the exact chip package.

The storage controller also performs wear leveling and address mapping, so the raw data must be correctly interpreted by the reader software. Finally, even a complete raw image may still contain encrypted data (FBE/FDE) that cannot be directly read without the required keys.

SoC-Specific Vendors

MediaTek

Best case: a storage device that is speed compatible with the target board and has a "clean" RPMB region.
Boot path: eMMC boots from Boot Partition 2/3. UFS-based MediaTek platforms boot from Boot A (LUN0) / Boot B (LUN1)

Worst case:a non clean RPMB still allows the device to boot but can produce app level failures, speed incompatible replacement storage will not function, such as the camera, may stop working.
An incorrectly configured boot path or corrupted firmware write will prevent boot.

Qualcomm

Best case: speed compatible, RPMB-clean storage
RPMB replaceability is described as chipset generation dependent:
Qualcomm chips at or below the Snapdragon 425 tier, the chipset itself can (re)generate clean RPMB keys, above that tier (450 and up), RPMB keys must be extracted from the original chip (if accessible) using specialized hardware ( "F64 box," a repair industry chip-reader tool)

If the device uses UFS, replacing the storage may not be possible because the RPMB sector is encrypted and cannot be directly extracted or transferred.

Samsung Exynos

Best case: speed compatible, RPMB clean storage.
Worst case: a non clean RPMB still boots the device but, on eMMC platforms, prevents unlocking the bootloader, on UFS platforms, the camera subsystem is reported to fail.
Speed-incompatible replacement storage (installing an older-generation eMMC/UFS chip from a legacy device) will not function.

HiSilicon (Kirin)

Best case: speed compatible, RPMB-clean storage.

RPMB replaceability is again described as chipset generation dependent:
Kirin 659 and below reportedly allow normal eMMC replacement because the chip can generate clean RPMB keys itself.
Kirin 710 and above reportedly cannot, requiring RPMB key extraction from the original chip via a specialized reader ("F64 box") if available.
UFS-based HiSilicon devices are described as not supporting RPMB replacement at all due to RPMB sector encryption.

Practical Case Study with HONOR X7d

I didn’t want to keep this research purely theoretical, so I decided to take it a step further and turn one of the techniques I studied into a real world practical experiment.

In mobile forensics, we often study acquisition methods through technical papers, training materials, and demonstrations. We learn about JTAG, ISP, and Chip-Off, understand how they work in theory, and explore the tools used to access device memory.

But understanding a technique on paper is one thing. Watching it happen on a real device is something entirely different.

I wanted to move beyond the theoretical side of mobile forensics and see what happens when these techniques meet real hardware, a real motherboard, tiny connection points, specialized equipment.

So, I decided to visit a mobile repair shop and turn the research into a practical experience

The main objectives were to:

  • Understand the physical structure of the target device and identify the relevant hardware components.
  • Explore connection using ISP acquisition approach
  • Observe how specialized equipment is connected to a smartphone motherboard.
  • Understand the technical and evidential limitations that remain after a memory read attempt.

At this stage, an important limitation became apparent

Android devices comonly use file-based encryption, with encryption keys and access conditions tied to the device's security architecture. Consequently, even when a forensic tool can read storage sectors or identify the userdata partition, the underlying content may remain encrypted. Without the appropriate keys and the necessary conditions for decryption, the acquired bytes may not reveal readable application files, messages, photographs, or other user content

This highlights one of the major challenges in hardware based mobile forensics. And the experiment demonstrated both the capabilities and the limitations of acquisition
